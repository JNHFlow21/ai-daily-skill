# LLM Batch 解析故障复盘与可复用经验

## 结论（为什么这次对了）
本次修复生效的关键点是：**对“批量输出不完整/结构异常”进行逐条回退补全**，并在单条场景直接使用单条生成；同时增强 JSON 解析鲁棒性。这样即使 LLM 只返回 1 条或返回对象而非数组，最终仍能保证每条新闻都有完整中文说明。

## 症状与表现
- tech/crypto 板块经常只有 1–2 条能生成说明，其余变成“待补充”。
- 错误日志：`LLM batch output is not a list`（尽管实际调用是 DeepSeek）。
- 现象集中在 **条目数量少**（去重后只剩 1 条或 2 条）的板块。

## 根因
1) **DeepSeek 在“单条/少量输入”时经常返回单对象**（或 `{items: {...}}`），而不是数组。
2) 原逻辑要求严格“数组类型”，一旦不匹配就整批失败，落回 `fallback_explain`。
3) JSON 解析过于脆弱：当响应包裹在代码块或夹杂文字时，解析失败。

## 为什么之前多次修复仍失败
- 修复只解决了“对象 vs 数组”的结构问题，但**没有处理“批量返回条数不足”**。
- 依旧依赖一次性批量输出，**没做逐条补全**，导致“半成功”时剩余条目直接 fallback。
- JSON 解析策略没有对“杂质文本、代码块、部分 JSON”做更强的提取。

## 最终有效的修复方案
1) **单条直接走单条生成**，避免 batch 结构歧义。
2) **批量解析后逐条补全**：
   - 对每个 item，如果 LLM 返回缺失或格式不对，直接用单条 LLM 再补上。
   - 这样即便 batch 只返回 1 条，其他条仍可完整生成。
3) **增强 JSON 解析**：
   - 去除 ```json 代码块；
   - 用括号平衡扫描，提取首个合法 JSON 片段。

## 可复用经验（Checklist）
- **少量输入时优先单条调用**（避免 batch 结构偏差）。
- **批量输出必须做长度与结构校验**，不足时逐条补齐。
- **解析 JSON 需容错**：允许代码块、前后噪声、非数组结构。
- **错误日志必须准确**：不要在 DeepSeek 路径写 “Gemini output …”。
- **优先稳定输出一致性**，而不是追求最低成本调用次数。

## 对后续类似系统的建议
- 建议所有 LLM 批量生成逻辑提供统一的“fallback per-item”机制。
- 监控指标应包含：batch 返回条数、解析失败率、fallback 触发率。
- 当结果用于发布（如 Telegram），必须保证单条完整性优先于吞吐量。
